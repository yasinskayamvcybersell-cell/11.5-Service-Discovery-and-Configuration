# Решение практической работы 11.5 Service Discovery and Configuration

## Контекст
На основе предыдущих работ спроектирована распределённая система:
- Микросервисы: Orders, Inventory, Pricing, Payments, Shipping, Cart, Notifications, Audit, Catalog.
- Событийная шина (Kafka/Event Bus), саги, REST API с идемпотентностью, ретраями, circuit breaker.
- Маркетологи хотят проверить несколько аналитических моделей (персональные рекомендации, динамическое ценообразование, изменение UI) на тестовой группе клиентов.

## 1. Стратегия проверки гипотезы на тестовой группе клиентов

### 1.1. Требования к эксперименту
- Разделение трафика: тестовая группа видит новую модель, контрольная – старую.
- Изоляция влияния: ошибки новой модели не должны нарушать основную систему.
- Сбор метрик для сравнения групп.
- Быстрый откат.

### 1.2. Варианты технической реализации

| Вариант | Описание | Плюсы | Минусы |
|---------|----------|-------|--------|
| **A. Feature flags в коде** | Условная логика `if (experimentGroup.contains(userId)) { newLogic }` | Простота, низкая задержка | Загрязнение кода, сложность управления |
| **B. Sidecar-адаптер** | Отдельный сервис `MarketingEnhancement`, вызываемый через API Gateway | Полная изоляция | Дополнительная задержка, сложность синхронизации |
| **C. Дублирование потребителей + CQRS** | Отдельный pipeline для построения проекций для тестовой группы | Гибкость, подходит для ML | Eventual consistency, доработка сервисов |

### 1.3. Выбранная стратегия
**Комбинация A и C + A/B тестирование на уровне API Gateway**:
- Для UI/UX изменений → **Feature flags** в `Frontend` и `API Gateway`.
- Для моделей, влияющих на цены, рекомендации, подбор товаров → **C (отдельный аналитический конвейер + проекции)**.
- **API Gateway** анализирует `X-Experiment-Group` и может маршрутизировать запросы к разным версиям сервисов.

### 1.4. Техническая реализация
1. **Определение групп**: на основе `userId` (consistent hashing). Группа передаётся через header `X-Experiment-Group`.
2. **Feature flag service** – централизованное хранилище конфигураций (Consul / LaunchDarkly).
3. **Для моделей с проекциями**:
   - Создаётся сервис `ExperimentProcessor`, подписанный на события (`OrderPlaced`, `CartUpdated` и др.).
   - Результаты записываются в отдельные таблицы / Redis.
   - Основные сервисы при запросе читают из проекций для тестовой группы.
4. **Мониторинг**: события помечаются полем `experimentGroup` и отправляются в `Audit` / `Analytics`.

## 2. Какие сервисы будут затронуты

| Сервис | Как затронут | Обоснование |
|--------|--------------|-------------|
| **API Gateway** | Добавляет header `X-Experiment-Group`, маршрутизация | Центральная точка входа для разделения трафика |
| **Frontend** | Feature flags для UI-элементов | Изменения интерфейса видны клиенту |
| **Catalog / Product** | Подмешивание рекомендаций из `ExperimentProcessor` | Модели маркетологов работают с ассортиментом |
| **Pricing** | Запрос экспериментальной цены (альтернативный источник) | Динамическое ценообразование |
| **Cart / Orders** | Feature flags для изменения процесса оформления | Эксперименты с воронкой продаж |
| **Notifications** | A/B тестирование промо-сообщений | Коммуникации с клиентами |
| **Audit / Analytics** | Добавление поля `experimentGroup` | Анализ результатов эксперимента |
| **ExperimentProcessor (новый)** | Новый микросервис для построения проекций и ML-моделей | Изоляция вычислительной нагрузки |

**Не затронуты** (при условии, что эксперимент не связан с ними): `Inventory`, `Payments`, `Shipping` – чтобы не нарушить целостность транзакционного ядра.

## 4. Автоматизация управления сервисами (ответ администраторам)
### 4.1. Критерии автоматизации
- Частота изменений → автоматизировать CI/CD.
- Критичность → автоматизировать мониторинг и восстановление.
- Общие компоненты → вынести в Chassis или Service Mesh.

### 4.2. Какие сервисы автоматизировать (и в каком порядке)
| Сервис | Автоматизация |	Причина |
|--------|---------------|---------|
| **API Gateway, Frontend**	| CI/CD + feature flags |	Частые изменения |
| **Catalog, Pricing** | K8s Deployment, autoscaling, ConfigMap |	Меняются при каждом эксперименте |
| **Notifications, Audit**	| Общая библиотека (Chassis) / Dapr	| Повторяющийся код |
| **ExperimentProcessor**	| Полная автоматизация (CI/CD, autoscaling)	| Будет часто меняться |
| **Orders, Inventory, Payments**	| Оставить ручную поддержку (только бэкапы)	| Критичны, меняются редко, рискованно автоматизировать |

### 4.3. Дорожная карта внедрения
- **Месяц 1:** GitOps (ArgoCD) + централизованный мониторинг.
- **Месяц 2:** Chassis / Dapr для Notifications, Audit, ExperimentProcessor.
- **Месяц 3:** Service Mesh (Istio) + HPA.
- **Месяц 4:** Автоматизация бэкапов и TLS.

### 4.4. Риски автоматизации и смягчения
| Риск	| Смягчение |
|--------|-----------|
| Ошибка в общей библиотеке (Chassis) уронит все сервисы |	Строгое версионирование, canary-обновления, тестирование |
| Усложнение отладки при Service Mesh	| Постепенное внедрение, трассировка |
| Конфигурационная сложность GitOps	| Ветки, approval, dry-run, CI-тесты |
| Потеря контроля над критическими сервисами	| Запретить автоматические деплои для Orders, Inventory, Payments |
| Затраты на разработку Chassis	| Использовать Dapr вместо самописного решения |

### 4.5. Итоговая рекомендация
- **Не автоматизировать всё** – оставить ручную поддержку для критических транзакционных сервисов.
- **Применить Dapr** – даёт building blocks для pub/sub, state, configuration, service invocation.
- **GitOps + мониторинг** – быстрый выигрыш в управляемости.
- Постепенный переход сервисов на Dapr, начиная с `Notifications` и `ExperimentProcessor`.
